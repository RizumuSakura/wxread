# 0002 用启动窗口取代对 GitHub 队列延迟的依赖

> 已被 [0003](0003-exactly-one-am-via-two-job-handoff.md) 取代：窗口只保证「落在凌晨」，不能保证「01:00 整」。

## 背景

`cron: '7 13 * * *'`（21:07 CST）是按"队列会延迟 4–7.5 小时"反推出的写法：延迟后落在凌晨 01:00–04:30，避开早上读书时段。

实测 6 次 schedule 的延迟在 4–7.5 小时之间抖动，而且队列没有任何承诺。一旦某天延迟只有 30 分钟，任务就在 21:37 开始跑两小时，正好和手机端抢进度；延迟到 8 小时以上则在早上 05:00 之后开始，同样撞上读书。

## 决定

1. 新增 `start_window.py`，以 Asia/Shanghai（固定 UTC+8，不依赖系统 tzdata）判断当前时刻，决定"立即开始 / 等到 01:00 / 跳过"。
2. 窗口为 01:00–05:00 CST 半开区间；20:00–24:00 睡到次日 01:00，00:00–01:00 睡到当日 01:00，05:00–20:00 直接跳过。
3. 跳过不是失败：脚本退出码 0，把 `window_ok=false` 写进 `GITHUB_OUTPUT`，阅读步骤用 `if` 跳过，缓存保存仍以 `always()` 执行，登录态照常落盘。
4. 手动触发保留 `force` 布尔输入（经 `WXREAD_FORCE_WINDOW` 环境变量传入，不写进 `run:` 里的表达式），用于随时验证。
5. 部署 job 的 `timeout-minutes` 从 360 提到 480：最多睡 5 小时等窗口，再加 121 分钟阅读。

## 后果

- 无论队列早到还是晚到，阅读都落在凌晨窗口内；晚到白天的运行直接放弃，第二天重来。
- 每次运行多一个几十毫秒的步骤，日志里有一行明确的窗口判断。
- 与 0001 一脉相承：把不确定性就地收敛成确定结果，而不是指望上游守时。
